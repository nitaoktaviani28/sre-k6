# Monochrome redesign: login gate, generated book covers, and confirm-before-action (v1)

The redesign reshapes the "Perpustakaan Digital" frontend around four behaviors the user asked for: force a login before the catalog is reachable, repaint the whole app in strict black-and-white, give every book a picture, and put an explicit confirmation in front of every state-changing action so nothing fires on an accidental click. The approach keeps the stack untouched (plain HTML/CSS/vanilla JS, nginx, no build) and is additive — `bookCoverSvg`, `UI.confirm`, and `UI.toast` are appended to `api.js` while `Auth`, `Api`, and `apiRequest` are left byte-for-byte intact. Covers are generated as deterministic inline SVG data-URIs, so no network or image assets are needed. Confirmations use a JS-injected overlay so no page needs extra HTML.

Watch for: the index login gate redirects but does not halt the inline script, so an unauthenticated visitor still fires catalog/category API requests before the browser navigates away (confirmed, low severity). Everything else — theme purity, cover coverage, confirm/feedback wiring, and preserved contracts — holds up.

**Verdict**: APPROVED

## High-level view

The login gate on the catalog works: `index.html` now calls `Auth.requireLogin()` at the top of its inline script, which redirects anonymous visitors to `login.html`. The one wrinkle is that the redirect is a `window.location.href` assignment with no early return, so the rest of the script (`loadCategories()`, `loadBooks()`) keeps running until navigation actually happens — a brief, invisible unauthenticated fetch, not a data leak.

The theme is genuinely monochrome. Every color token in `style.css` is black, white, or a gray; there are no residual hues, named colors, or non-gray hex/rgb values anywhere in the file. Status is communicated through fill and border weight rather than color (available = solid black badge, unavailable = white/gray outline; error toast = white card with a heavy border, success toast = solid black), which is the right way to stay monochrome without losing signal.

Every book gets a cover. `bookCoverSvg(book)` builds a deterministic grayscale SVG (initials + truncated title/author, shade seeded from title+author) returned as a `data:image/svg+xml` URI, so coverage is total and offline. The card markup HTML-escapes the SVG text via a locally-defined `escapeHtmlAttr`, and the CSS additionally forces `filter: grayscale(1)` on the image as a safety net.

All state-changing actions now route through `UI.confirm()`, a promise-based injected modal, before touching the API: borrow (index), return (my-loans), and delete-book / delete-category / edit-save (admin). Each caller disables its trigger button and swaps in a "Memproces…/Menyimpan…" label during the request, then emits a `UI.toast` plus the existing inline alert on success or failure. The admin edit-save handler correctly calls `e.preventDefault()` before the async confirm, so the form doesn't reload out from under the dialog.

Contracts are preserved and nothing out of scope was touched: no backend, docker, or CI changes; README/frontend-README edits only swap "biru muda & putih" for "hitam & putih (monokrom)". Add-category is the one action deliberately left without a confirm — reasonable, since it's non-destructive and gated by a non-empty input.

### Login gate on the catalog fires a stray request before redirect

`index.html` adds `Auth.requireLogin()` as the first statement of its inline script. `requireLogin` sets `window.location.href = 'login.html'` when there's no token but returns normally, and the caller does not check the result:

```js
Auth.requireLogin();
renderNavbar('index');
// ...
loadCategories();
loadBooks();
```

Because assigning `location.href` schedules navigation rather than stopping execution, an anonymous visitor still runs `loadCategories()` and `loadBooks()`, each issuing an authless `fetch` to the API, before the browser leaves the page. No catalog data reaches the screen (the page navigates away), so the gate meets the user's intent of "login dulu sebelum masuk ke perpustakaan," but the stray requests are avoidable. `my-loans.html` and `admin.html` share the same pattern, but their gating predates this change and is out of scope here — only the `index.html` call is new. A one-line guard (`if (!Auth.isLoggedIn()) return;` after `requireLogin`, or wrapping the bootstrap calls) closes it. (confirmed)

### Cover escaping and cross-page load order

`bookCoverSvg` interpolates the title/author into the SVG text nodes, escaped through `escapeHtmlAttr` — defined locally in `api.js` rather than relying on nav.js's `escapeHtml`, so the helper stays safe on pages that don't load nav.js. The card `alt` text does use nav.js's `escapeHtml`, but only `index.html` builds card markup with `bookCoverSvg`, and it loads nav.js before its inline script runs, so the load order holds and there's no undefined-reference risk. (confirmed)

### Confirm-before-action wiring and the form-submit ordering trap

`UI.confirm()` resolves `true` only on the confirm button (or Enter) and `false` on cancel/backdrop/Escape; every mutating caller awaits it and bails on `false`. The correctness point worth calling out is in `admin.html`'s edit-save, which lives in a `<form>` submit handler: it calls `e.preventDefault()` *before* awaiting `UI.confirm`, so the native submit is cancelled and the page can't reload while the dialog is open. Had `preventDefault` come after the await, the default submit would have fired first and reloaded the page mid-confirm. Delete-book, delete-category, borrow, and return are plain click handlers without this hazard. (confirmed)
